# Configuration inventory

The audit uses exact attribute readers, model validators, job producers and resource lifecycles. A text occurrence is not evidence of an effect. This inventory records the supported surface and classifications; runtime behavior tests accompany the implementation.

## Resolution and timing

Process environment beats `.env`; explicit construction values are used by embedded callers/tests. Alias choices are ordered as shown and case-insensitive. Direct secret inputs beat all `_FILE` variants; file contents are stripped except SSH key/known-host material. Restart inputs stay fixed for a process. Live policy uses DB override > `runtime.toml` > the role’s resolved environment/defaults. Thread environment pins remain ceilings. The backend registry uses its separate validated `backends.toml` reload path.

API/controller notifications and fallback polling update policy; agents recover missed notifications by bounded authenticated polling. Each operation captures one snapshot; existing jobs/manifests keep their serialized limits. Changed policy compares against existing durable attempts, timestamps and rate windows. New policy never clears stop states or resets budgets. One-shot cloud jobs fetch the same override layer before starting work.

## Settings models

There are **88 unique settings fields**: **39 live model fields**, **47 restart inputs**, and **2 live registry collections**; including the three native analysis controls, the runtime policy has **42 live keys**. The model field count is unchanged; this audit adds 32 working live controls, including native inference batching. Cloud-submit attempts were initially proposed as live, then retained as restart-only after the persisted edge-trigger audit. Three native controls (two thread pools plus inference batch) are live outside the Settings models. The model split has 39 live fields and 49 other fields (47 restart + 2 registry). No still-consumed setting is removed merely to reduce the count.

## Removed and intentionally separate controls

The earlier cleanup already removed nine inert Settings declarations (`analysis_fine_window_sec`, `analysis_coarse_window_sec`, `analysis_fine_min_sec`, `worker_health_check_interval`, `output_path`, `api_host`, `api_port`, `push_ssh_host`, `api_tls_sans`; see the baseline audit for grouped counts). This audit does not remove their still-consumed direct environment counterparts. It removes the dev-overlay `PHAZE_DEBUG` input: it was never an accepted alias and had no effect. `UID` and `GID` example inputs are also removed: neither was interpolated by Compose, accepted as an image build argument or read by the application. Container identities remain fixed by their images; a Compose user/mount ownership override is the real deployment mechanism. The consumed `DEBUG` setting remains as SQLAlchemy statement echo, distinct from live application log detail. Set `PHAZE_LOG_LEVEL=DEBUG` for normal diagnostics; set legacy `DEBUG=true` deliberately for SQL echo.

`database_url` and `queue_url` address different clients/authorities (ORM application data versus raw-libpq broker); equal deployment defaults do not make them duplicates. `scan_chunk_size` is throughput policy while `agent_file_chunk_max` is a request-schema safety ceiling. `push_max_attempts`, submit attempts, lifetime chains, node-loss budgets and cooldowns count different events and retain distinct safety semantics. Media and runtime-file observers watch different roots/processes and cannot share a polling toggle.

No aliases were renamed or consolidated. Existing alias-choice and direct-secret-over-file precedence remain covered by characterization/config tests; absent/unknown direct inputs retain their existing ignore behavior. Invalid live changes reject the whole candidate and preserve the last-good snapshot/resources.

The standalone watcher owns its own policy context, polls independently every 30 seconds, and supports SIGHUP for the local file layer. Its pending entries preserve captured settle/cap values, the one-shot grace flag and move lineage across changes. It never reports agent liveness or changes worker queue identity.

Additional third-party SDK namespaces (other optional `OTEL_*`, AWS credential/profile variables and Kubernetes client configuration) remain library-owned. Their defaults/parsing/resources are outside the application Settings contract; Phaze does not claim to validate arbitrary SDK variables or expose them as successful runtime overrides.

## Wire compatibility and role effects

New agents explicitly request policy wire version 2 through `X-Phaze-Config-Version`; unversioned agents receive the original 10-key int/string envelope, so retry arrays cannot break an older parser before unknown-key filtering. Each envelope has its own content digest. New clients remain compatible with older servers that ignore the header. A newer agent is required to adopt new policy keys.

Shared Settings declarations do not imply every process consumes every field. SQLAlchemy engine/pool inputs, dev seeding, schema migration and dashboard mounting belong to API/controller processes. Worker queue and default-job policy belongs to controller/agent enqueuers; lane concurrency and analysis child limits belong to agent workers. Scan/model/SSH identity belongs to the corresponding agent operation. The media watcher has its own discovery policy context and subscriptions. One-shot jobs fetch policy and apply log detail while retaining their explicit friendly-console default; they never start agent heartbeat machinery. Credentials and registry resources remain with their existing owners.
