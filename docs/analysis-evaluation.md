# Phaze analysis replacement evaluation, version 2

Status: **UpCloud baseline in progress; no replacement measured**. `phaze-iq64v` remains on a local bead branch. Version 2 changes the execution host and reference-label plan before any candidate run. The eight-file production sample is in `docs/evaluation-phaze-iq64v-corpus.json`. It was selected in one read-only query against Phaze on lux, filtered to completed analyses owned by nox, using one deterministic SHA-seeded selection per format and duration band. The manifest records file IDs, SHA256, duration, codec, and source sample rate; it contains no archive pathname or filename. The sample totals 10.27 audio hours and has MP3, AAC/M4A, FLAC, 44.1 kHz and 48 kHz, and short, medium, long, and very long bands. SHA-named copies and models downloaded directly on the UpCloud host are already staged. This is primarily a **performance and contract** sample; available database tags provide only partial quality evidence.

## Decision rule

A candidate passes only if **all** of these hold:

1. It produces every Phaze semantic result below. More attributes are welcome. The current 33 classifier-variant arrays are implementation detail, not a required output. A candidate supplies an adapter to Phaze's stored schema and downstream consumers; a JSON blob that merely validates at the HTTP boundary is insufficient.
2. It covers the complete audio timeline at least as finely as today's 30-second fine tier and 180-second coarse tier. Finer or overlapping windows are allowed. The only tolerated fine-tier omission is a trailing segment shorter than 15 seconds, matching today's rule. Every absent or failed window is counted explicitly.
3. It preserves the current Phaze result families and timeline behavior using a frozen read-only snapshot of the homelab `analysis` and `analysis_window` rows as the **incumbent reference**. Numerical equality is not required. Compare semantic coverage, distributions, per-file and per-window disagreement, and downstream projections; predeclare tolerances before a candidate run. Separately, score any source labels that did not come from the analyzer. Missing source labels remain **unscored**, not assumed correct. An incumbent reference alone cannot prove accuracy noninferiority against the audio.
4. On the **same UpCloud host** as the measured baseline, pinned input copies, image/model versions, resource allocation, and concurrency, it uses at most **half the current analyzer's end-to-end wall time** on the paired corpus, with no worse failure rate, no coverage regression, and no larger resource-limit breach. Report the paired per-file ratios as well as the total; one very long file must not hide regressions elsewhere. The 2× threshold is the initial performance gate; change it only by versioning this contract before seeing candidate results. Also report whether each file finishes faster than 1× playback.

The old 0.56–0.79×-duration measurements in `docs/spikes/phaze-b2qs9-exhaustive-analysis-measurement.md` are historical context, **not** the baseline for this decision. The baseline must use the version that is actually deployed when the isolated run occurs.

## Result inventory and consumers

| Level | Required semantic output | Current source and consumers |
| --- | --- | --- |
| File | BPM and musical key (`<note> <major/minor>`) | `analysis` columns; file views, set/record facts, Camelot lookup |
| File | Seven named mood scores: acoustic, electronic, aggressive, relaxed, happy, sad, party | callback `mood` dict from `analysis_wire`; stored as a bounded string summary |
| File | Danceability; ranked genre/style scores; dominant style | `analysis` columns; genre grouping, similarity, proposals |
| File | Representative gender, tonal/atonal, voice/instrumental characteristic scores | the analysis child returns these in its representative `features`; the present callback does **not** forward that top-level object |
| Fine window | Index, start/end, BPM, musical key, read-time Camelot | `analysis_window`; timeline and harmonic/set projection |
| Coarse window | Index, start/end, mood, style, danceability, seven mood scores plus danceability/gender/tonality/voice (11 fixed scores), energy | `analysis_window` and `set_projection`; mood river, glyph, energy arc, set profiles |
| Both tiers | Natural total/analyzed counts and explicit failure gaps | `analysis` progress/completion, operator timeline |

The contract is grounded in `analysis_models.py`, `analysis_windows.py`, `analysis_wire.py`, `models/analysis.py`, `schemas/agent_analysis.py`, `routers/agent_analysis.py`, `set_projection.py`, `set_projection_writer.py`, and `proposal_context.py`. The child returns file-level `features` copied from one representative coarse window. The callback's `AnalysisWritePayload` omits that field; on current writes, the aggregate database `features` is primarily the wire overflow (danceability and energy), while the full characteristic predictions persist per coarse window. The persisted `style` list is aggregated over that timeline. `proposal_context` forwards **the stored aggregate** `features`, not the child's representative feature object. A replacement's adapter must preserve the meaning of these actual stored consumers. `set_projection_writer.positive_class_vector` currently reads Essentia-shaped variant predictions from coarse windows, so it needs a deliberate neutral-score adapter or schema migration before rollout. Do not manufacture three fake variant arrays to satisfy it.

The benchmark runner accepts the current child protocol (`--protocol current`) and a replacement-neutral terminal result (`--protocol neutral`) with the same file/window semantic fields plus `mood_scores`, `energy`, and `camelot`. It checks the wire shape, 11-score completeness, window geometry, and coverage. Neutral predictions need ranked `{name, score}` style rows. It does not assert equality of numbers to Essentia.

## Homelab reference and source-label evidence

The homelab Phaze database is the operational reference for **what Phaze currently returns**. Export a frozen, read-only snapshot for the eight manifest IDs from `analysis` and `analysis_window`, including completion markers, result families, window coordinates, and 11-score projections. Preserve the database snapshot time and a SHA256 of the export. Use it to check compatibility and characterize numerical disagreement. Do not copy path, filename, artist, title, or album fields into the tracked report. The current analyzer produced these rows, so labeling them independent accuracy ground truth would make the evaluation circular. A candidate may legitimately disagree with them and be better.

`metadata.genre` and embedded audio tags are separate source data. In a read-only coverage check on 2026-09-30, five of the eight sample IDs had a nonempty `metadata.genre`; all eight had `analysis` and fine/coarse window rows; none had a linked `tracklists` row. The sampled raw tag keys contain no BPM or key fields. Preserve the source tag values privately by SHA, inspect their provenance and taxonomy, and map them to the candidate's style taxonomy before any genre scoring. An embedded genre tag is a partial, possibly noisy reference, not automatic proof of the correct style. There are currently no DB source labels for BPM, key, moods, danceability, gender, tonality, voice, or transitions in this eight-file sample.

The source-label file is JSON with `schema_version: 1` and an `annotations` array; see `docs/analysis-evaluation-labels.example.json`. Every record uses `sha256` and may provide `bpm`, `key`, `binary` (a mapping from an `MOOD_ORDER` name to 0 or 1), and `genre` (one or more accepted labels in the **same** taxonomy as Phaze's ranked style output). Each record requires a source, annotator count, and ambiguity/confidence note. For a source audio tag, identify it explicitly as a tag rather than a listening annotation; the scorer's `annotators` field can represent one tag source but does not establish human review. Keep a separate held-out split from any candidate training or threshold tuning. Music with a disputed perceptual tempo or key remains explicitly ambiguous; do not force it into a single false reference.

The supplied scorer reports strict ±2% BPM accuracy, octave-aware ±2% accuracy, absolute BPM error, exact and [MIREX-weighted key](https://music-ir.org/mirex/wiki/2020%3AAudio_Key_Detection) scores, per-attribute F1 and Brier score at a declared 0.5 threshold, and genre top-1/top-5. Evaluate each of the 11 characteristics separately. For gender, tonality, and voice/instrumental, first document which physical class a score represents; the present `positive_class_vector` selects a class by its label convention, so a numeric value without that mapping is **not** a valid human-label comparison. Public [MTG-Jamendo classification annotations](https://github.com/MTG/mtg-jamendo-dataset/blob/master/derived/music-classification-annotations/README.md) cover most named characteristics but do not directly establish correctness of Phaze's Discogs400 hierarchy or changing moods within a multi-hour set. Those need independently annotated Phaze-representative excerpts.

For transition quality, compare time-stamped tempo, key, mood, and style changes to the frozen DB windows as an operational reference. Report event precision/recall with matching tolerance no larger than one corresponding existing window, window-aligned disagreement, and worst-case false-change rate. These are **agreement** metrics until separately labeled transitions exist. The initial scorer covers file-level source labels only. For independently supported quality fields, the initial noninferiority margins are no more than two percentage points below baseline accuracy/F1/top-k/transition recall and no more than 0.02 above baseline Brier; report paired uncertainty and per-stratum results. Mark result families without independent source labels **accuracy unverified**. Such a result can establish a faster, contract-compatible candidate, but cannot support a claim that its audio classification is at least as accurate as current Phaze.
