## Verdict in one paragraph

**Seeking is not merely feasible, it is a ~170-line change, and it is sample-exact.** A patched
`AudioLoader` seeks with `av_seek_frame`, decodes forward through a 0.5 s preroll and trims to the
exact sample, and its output is **bit-identical** to the decode-and-discard path on WAV, MP3 and
FLAC, and on Ogg/Opus once a second, independent bug is fixed. The one format that is not
bit-identical, AAC, is not the patch's fault and cannot be fixed by anyone: **Perceptual Noise
Substitution** synthesises noise bands from a PRNG seeded by the whole decode history, so the
residual is insensitive to preroll across a 200× sweep (0.05 s → 10 s) and **vanishes entirely**
when the same audio is re-encoded with `-aac_pns 0`. Nothing measurable moves at the product
level: **BPM is exact and key is identical in every case**, with the largest descriptor
disagreement anywhere being **9.3 × 10⁻⁵ relative**. The performance result is the structural one
phaze has wanted for months — decode stops being `O(total duration)` and becomes `O(span asked
for)`. Decoding one 30 s window 1800 s into a 1-hour file falls from **2.142 s to 0.086 s (25.0×)**
on a 44.1 kHz source, and from **53.375 s to 0.235 s (227.4×)** on a 48 kHz source, where
libsamplerate dominates; decoding the second half of a file costs almost exactly half of decoding
all of it (1.065 s vs 2.100 s; 9.925 s vs 19.681 s; 8.563 s vs 16.947 s), which is the definition
of the property that was missing. Reproducing phaze's **actual chunked fan-out**, `endTime`
replaces the `phaze-w55w1` `Trimmer` gate outright — **every non-final chunk gets cheaper, by
−45.2% / −41.4% / −7.2%**, against the 18.5–36% `phaze-b2qs9` §4c measured for the gate — with one
reproducible **+23.1% regression** on the single least favourable configuration (final chunk,
60 windows, ratio 1.0 so decode is a `fastcopy`) that is **downstream of the loader and is not
explained**; it is flagged, not explained away, and it must be understood before adoption.
**Building essentia from source cost 1 m 19 s** of wall clock
for a full 328-task build on an 8-performance-core laptop, and **13.1 s** to rebuild after
touching `audioloader.cpp` — but it required patching essentia first, because
`src/python/wscript` imports `distutils`, **removed from Python in 3.12**, so the bindings cannot
be built on phaze's 3.14 at all without a fix. Two further defects surfaced that are worth more to
phaze than they cost: `AVCodecContext::pkt_timebase` is never set (silently wrong frame
timestamps), and `Trimmer` converts seconds to samples in `float32`, so **phaze's own analysis
windows today drift off the exact sample grid by up to 8 samples at 1 hour and ~128 samples at 12
hours** — a reproducibility defect nobody had noticed, which the seek design incidentally fixes.
The honest limitation: this was built and measured **without TensorFlow**, so the source-build cost
for phaze's actual `essentia-tensorflow` configuration is **not** established by this spike, and
`phaze-a51jo` still needs that number.

### 1a. The synthetic corpus

Generated by [`make-synthetic-corpus.sh`](phaze-han03/make-synthetic-corpus.sh) in **5 m 50 s**.
The signal is one deterministic closed-form function of `t`, so the same command reproduces the
same samples anywhere, and it is shaped to serve three purposes at once:

- an A3/C4/E4 triad (220 / 261.626 / 329.628 Hz) re-triggered every **0.5 s = 120 BPM** with an
  exponential decay and a sharp transient, so **BPM and key are well defined** and can be compared
  between a seeked and an unseeked read;
- a slow chirp, so the waveform is **globally unique**. Without it the signal is exactly periodic
  at 0.5 s and a sample-accuracy test could not tell a correct seek from one wrong by a whole
  number of bars;
- no RNG anywhere, so the lossless reference is bit-reproducible.

### 2b. Two things blocked the build, and one of them is upstream's

1. **`src/python/wscript` imports `distutils`, removed from the standard library in Python 3.12**
   (PEP 632). On phaze's Python 3.14 the configure step dies with `ModuleNotFoundError: No module
   named 'distutils'` before compiling a single file. Both uses are
   `distutils.sysconfig.get_python_lib()`, whose documented replacement is
   `sysconfig.get_paths()['purelib']`. **This is a hard blocker on building the Python bindings
   from source on any currently supported Python**, and it is patch 0001.
1. Machine-local, not upstream's problem, recorded so the next person does not lose an hour:
   this workstation's Command Line Tools ship an **empty** `usr/include/c++/v1` (1 file, where the
   SDK's copy has 193), so bare `clang++` cannot find `<map>`. Worked around with a two-line
   compiler wrapper injecting `-isystem …/MacOSX.sdk/usr/include/c++/v1`.

### 2c. What this does NOT tell us — read before quoting the number

The build was configured **without TensorFlow**, which excluded 11 algorithms
(`TensorflowPredict*`, `TempoCNN`, `PitchCREPE`, …), plus Gaia (`GaiaTransform`,
`MusicExtractorSVM`) and Chromaprint (`Chromaprinter`). That is fine for this spike — `AudioLoader`
and `MonoLoader` do not touch any of them — but it means **1 m 19 s is a floor, not the answer to
`phaze-a51jo`'s question.** The phaze image uses `essentia-tensorflow`, whose wheel bundles
`libtensorflow 2.20.0`; reproducing that configuration requires a `libtensorflow` C library, a
`--with-tensorflow` configure, and a manylinux/cp314 wheel build for **linux x86_64**, none of
which was attempted here. The relevant unknowns for a patched build are (a) obtaining
`libtensorflow` 2.20.0 headers/libs, (b) whether upstream's own wheel recipe is reproducible, and
(c) linux-vs-macOS toolchain differences. **`phaze-a51jo` should not treat this as settled.**

## 3. The prototype

Three commits against `b9fa6cb`, exported as `git format-patch` series in
[`phaze-han03/patches/`](phaze-han03/patches/). They **apply cleanly with `git am` to a pristine
upstream checkout** (verified against a fresh clone), and they are deliberately split the way they
should be submitted upstream — one build fix, one bug fix, one feature.

| patch | subject | lines |
| --- | --- | ---: |
| `0001` | `build: use sysconfig instead of the removed distutils in the python bindings` | 4 |
| `0002` | `fix(audioloader): set pkt_timebase so decoded frame timestamps are correct` | 8 |
| `0003` | `feat(audioloader): add startTime/endTime seeking to AudioLoader and MonoLoader` | ~170 |
| `0004` | `feat(easyloader): let EasyLoader and EqloudLoader seek instead of decode-and-trim` | 57 |
| `0005` | `test(io): cover startTime/endTime seeking and its boundary cases` | 323 |

`0004` and `0005` were added by `phaze-0ni3v`, which also folded two semantic corrections into
`0003` (truncation rather than rounding in the seconds→samples conversion; an empty range is no
longer an error). The exported `0003` here is therefore the corrected one, not the one this spike
originally measured — see
[`phaze-0ni3v-easyloader-seek.md`](phaze-0ni3v-easyloader-seek.md) §1.

### 3a. How the seek works

Exactly the shape #771's own maintainer sketch proposed, plus the part the sketch does not
mention, which is the part that actually took the work.

- `openAudioFile()` ends with `seekToStartTime()`: `av_seek_frame(..., AVSEEK_FLAG_BACKWARD)` to
  `startTime − 0.5 s`, then `avcodec_flush_buffers()` and a `swr_init()` to drop converter state.
- `process()` returns `FINISHED` once `endTime` has been produced instead of reading to EOF.
- `copyFFmpegOutput()` trims the partial frames at both ends of the slice.

**The 0.5 s preroll is the whole correctness story.** A compressed stream can only be seeked to a
packet boundary, and that packet is not independently decodable — MP3 carries a bit reservoir
between frames, every MDCT codec needs the previous window. So the patch deliberately lands
*early*, decodes forward discarding output, and starts producing at the exact requested sample.
The exact sample is located from the **first decoded frame's pts**, not assumed to be the packet
boundary — which is why patch 0002 is a prerequisite rather than a nicety.

**Failure is soft everywhere it can be.** A seek that fails, or a stream with no usable
timestamps, falls back to decoding from the beginning and discarding — i.e. to exactly today's
behaviour. No format that works now can break; the worst case is that it stays slow.

### 3b. `pkt_timebase` — the bug that had to be fixed first

`AVCodecContext::pkt_timebase` is never set in `openAudioFile()`, so it keeps its `0/1` default.
libavcodec uses it whenever it moves a timestamp by a sample count — most importantly when it
discards a codec's initial padding (Opus pre-skip, AAC/MP3 encoder delay) and then advances
`frame->pts` by the number of samples skipped. Against an invalid time base that adjustment is
meaningless.

Nothing consumed `frame->pts` before, which is why this was invisible. It becomes load-bearing the
moment timestamps are used to locate the decoder in the stream. **Measured: a constant +312-sample
(6.5 ms) offset on Ogg/Opus — exactly Opus's mandated pre-skip.** Setting `pkt_timebase` before
`avcodec_open2()` is the documented requirement and changes no existing output.

## 4. Correctness — verified before any performance was celebrated

Re-runnable as [`phaze-han03/verify_accuracy.py`](phaze-han03/verify_accuracy.py).

### 4a. `AudioLoader` at the native rate — the seek in isolation

Slices of 5 s taken at 1.0 / 37.5 / 123.456 / 300.0 s, compared against the decode-and-discard
reference.

| container / codec | bit-identical at all four offsets | worst `max|diff|` |
| --- | --- | ---: |
| WAV / pcm_s16le | **yes** | 0 |
| MP3 / mp3float | **yes** | 0 |
| FLAC | **yes** | 0 |
| Ogg / Opus | **yes at 3 of 4**; one offset differs by a single ULP | **5.96 × 10⁻⁸** (= 2⁻²⁴) |
| MP4 / AAC-LC | **no** | 3.02 × 10⁻² |

### 4b. The AAC residual is the codec's, not the patch's — and here is the proof

Two independent experiments, either of which alone would be suggestive and which together are
conclusive:

1. **It does not respond to preroll.** Rebuilt at four preroll lengths spanning 200×:

   | preroll | 1.0 s | 37.5 s | 123.456 s | 300.0 s |
   | ---: | ---: | ---: | ---: | ---: |
   | 0.05 s | 1.85e-02 | 3.19e-04 | 3.02e-02 | 7.98e-05 |
   | 0.5 s | 2.05e-02 | 3.19e-04 | 3.02e-02 | 7.98e-05 |
   | 2.0 s | 2.12e-02 | 3.19e-04 | 3.02e-02 | 7.98e-05 |
   | 10.0 s | 2.12e-02 | 3.68e-04 | 2.59e-02 | 7.02e-05 |

   A decoder-warm-up effect would fall off with preroll. This is flat. **No finite preroll fixes
   it**, which means the difference depends on state that is not reconstructible from a bounded
   history.

1. **It disappears when the encoder stops using PNS.** Re-encoding the identical audio with
   `ffmpeg -c:a aac -aac_pns 0` makes the seeked read **bit-identical at all four offsets**.

**Perceptual Noise Substitution** replaces noise-like bands with locally synthesised noise from a
PRNG whose state advances every frame from the start of the stream. Reproducing it after a seek
would require decoding from frame 0 — i.e. would require not seeking. This is a property of AAC,
it applies equally to `ffmpeg -ss` and to every other seeking decoder in existence, and the
affected content is **synthesised noise by construction**, chosen by the encoder precisely because
its exact waveform is perceptually irrelevant.

### 4c. `MonoLoader` — the resampler, not the seek, is the residual

| source | tier rate | ratio | bit-identical | `max|diff|` | relative RMS |
| --- | ---: | ---: | --- | ---: | ---: |
| MP3 44.1 kHz | 44 100 | **1.0** | **yes** | 0 | — |
| MP3 44.1 kHz | 16 000 | 0.3628 | no | 3.19e-02 | **−49.0 dB** |
| AAC 44.1 kHz | 44 100 | **1.0** | no *(PNS only, §4b)* | 3.80e-04 | **−98.0 dB** |
| AAC 44.1 kHz | 16 000 | 0.3628 | no | 3.24e-02 | −49.0 dB |
| Opus 48 kHz | 44 100 | 0.91875 | no | 1.77e-02 | −56.8 dB |
| Opus 48 kHz | 16 000 | 0.3333 | no | 3.31e-02 | −50.1 dB |

Read the two ratio-1.0 rows against the rest: MP3 is **exact**, and AAC's −98.0 dB is the PNS
residual of §4b and nothing else. Every row at −49 to −57 dB is a row where libsamplerate ran.

The split is explained entirely by `Resample`: streaming `resample.cpp` has an
`if (_data.src_ratio == 1.0)` branch that `fastcopy`s and never touches libsamplerate, so the
ratio-1.0 tier is stateless and stays exact. When libsamplerate *does* run, its output depends on
how much input it has already consumed — filter history plus a phase accumulator — so a cold start
at the seek point differs from a converged one.

The error is **uniform across the window, not a startup transient** (rms per decade: 2.17e-03 in
the first millisecond, then 9.5e-04 / 5.8e-04 / 6.3e-04 / 6.3e-04 out to the end), which rules out
FIR warm-up and points at accumulated phase. Confirmed by feeding the resampler progressively more
history:

| preroll fed to the resampler | relative RMS |
| ---: | ---: |
| 0 s | −49.0 dB |
| 0.5 s | −49.1 dB |
| 2 s | −49.3 dB |
| 10 s | −50.6 dB |
| **60 s (= full history, startTime 0)** | **−78.5 dB**, and the window head becomes **exactly zero** |

With full history the *only* remaining difference is the **last ~11 samples**, a resampler tail
effect at `endTime` that exists in the current phaze code path too.

**This bounds the upstream design question honestly:** making `MonoLoader` bit-exact under
resampling requires prerolling *through* the resampler and discarding after it, which is a change
to the composite's shape, not a parameter. Patch 0003 deliberately does not attempt it, and the
commit message says so.

### 4d. The question that actually decides it — does anything move?

Same window, seeked vs decode-and-discard, across codecs and both tier rates:

| file | tier rate | BPM | key | key strength | loudness | centroid |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| mp3 | 44 100 | **exact** | **same** | exact | exact | exact |
| mp3 | 16 000 | **exact** | **same** | 4.66e-05 | 6.97e-07 | 7.77e-07 |
| m4a | 44 100 | **exact** | **same** | 1.25e-07 | 9.45e-08 | exact |
| m4a | 16 000 | **exact** | **same** | 9.28e-05 | 4.49e-06 | 3.93e-07 |
| opus | 44 100 | **exact** | **same** | 3.66e-06 | 9.90e-06 | 1.60e-06 |
| opus | 16 000 | **exact** | **same** | 4.80e-05 | 8.83e-06 | 2.48e-06 |

**BPM is exact and key is identical in all twelve comparisons.** The largest disagreement anywhere

TensorFlow (§2c). What *is* established is that their **input** differs by at most −49 dB and that
every classical descriptor measured is unmoved.

## 5. The measured win

Re-runnable as [`phaze-han03/bench_decode.py`](phaze-han03/bench_decode.py).

### 5a. Decode becomes `O(span)` instead of `O(duration)`

On `synth-3600s*.mp3`. `EasyLoader` is the control: it exposes the same `startTime`/`endTime` and
has no seek, so it is what phaze's per-window fallback rung pays **today**.

Run twice: once at load average ~5.9 (the contended run, all the chunk measurements were taken
alongside it) and once at ~3.2. Both are given, because the spread between them is the honest
error bar on every absolute figure in this document.

| case | full `[0, 3600)` | seek `[1800, 3600)` | seek **one window** | `EasyLoader` one window | **speedup** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 44.1 kHz src → 44 100 (ratio 1.0, fastcopy) | 2.100 / 2.087 s | **1.065 / 1.013 s** | **0.086 / 0.048 s** | 2.142 / 2.064 s | **25.0× / 43.0×** |
| 48 kHz src → 44 100 (ratio 0.91875, SRC) | 19.681 / 19.402 s | **9.925 / 9.757 s** | **0.235 / 0.195 s** | 53.375 / 52.490 s | **227.4× / 268.6×** |
| 44.1 kHz src → 16 000 (coarse tier, SRC) | 16.947 / 16.667 s | **8.563 / 8.391 s** | **0.921 / 0.864 s** | 28.308 / 27.760 s | **30.7× / 32.1×** |

The full-file and half-file columns agree between runs to **within 1.5%**; the single-window column
is the one that moves (up to 1.8×), because at 48–86 ms it is small enough for scheduler noise to
matter. **The speedups are therefore lower bounds, not best cases** — the contended run is the
conservative one and is what the verdict quotes.

Two things to read off this table.

1. **`seek [1800, 3600)` is almost exactly half of `full [0, 3600)` in all three rows** — 50.7%,
   50.4%, 50.5%. That *is* the property that was missing. `phaze-esut` §8's "linear in *total*
   duration, independent of window length" is repealed: cost is now linear in the span requested.
1. **The win is largest exactly where phaze hurts most.** The 48 kHz row is 227× because
   libsamplerate dominates that decode (19.681 s vs 2.100 s for the same duration at ratio 1.0),
   and seeking removes proportionally more of it. This independently corroborates `phaze-b2qs9`
   §4d's finding that source sample rate is a first-order term — and it says the fix for that term
   is seek, not tuning.

### 5b. What this would mean for the chunked pipeline

`phaze-w55w1`'s chunk gate recovers **18.5–36%** of a non-final chunk's decode and, per
`phaze-b2qs9` §4b, **does not scale with the chunk boundary**. With real seek, chunk *k* decodes
only its own span, so the `Trimmer` gate becomes unnecessary and D-07's `duration × (K+1)/2` model
is replaced by `duration` — one file-length decode per tier, total, regardless of chunk count.
On `<set-05>`'s 12 fine chunks that is ≈ 1 310 s of gated decode today against a floor of one pass.

**This spike does not claim that end-to-end number**, because it never ran an end-to-end analysis
(§9.3). What it does establish is the per-chunk half of it, measured in §5c: the decode term
collapses, and the gate is superseded.

### 5c. Chunk-level fan-out — measured, and deliberately not used as the headline

`bench_seek.py` reproduces `_decode_windows_streaming`'s actual network (one `MonoLoader`, a
`Trimmer` gate straight off the loader for non-final chunks, `Scale` → `Trimmer` → `Pool` per
window) in both arms.

Both arms run in a fresh process, adjacently in time, and the whole matrix twice. **Repeatability
is within 2% on every cell**, so the deltas below are signal, not host noise.

| file | tier rate | chunk | final? | windows | baseline (s), 2 runs | seek (s), 2 runs | **delta** | PCM md5 |
| --- | ---: | ---: | :---: | ---: | ---: | ---: | ---: | :---: |
| `synth-3600s-48k.mp3` | 44 100 | 0 | no | 60 | 107.37 / 107.37 | 59.36 / 58.36 | **−45.2%** | same |
| `synth-3600s-48k.mp3` | 44 100 | 1 | yes | 60 | 58.91 / 58.30 | 59.22 / 58.22 | +0.2% | differs |
| `synth-3600s.mp3` | 44 100 | 0 | no | 60 | 53.44 / 54.46 | 49.74 / 50.37 | **−7.2%** | same |
| `synth-3600s.mp3` | 44 100 | 1 | yes | 60 | 40.23 / 40.43 | 49.42 / 49.86 | **+23.1%** | same |
| `synth-7200s.mp3` | 16 000 | 0 | no | 30 | 55.34 / 54.12 | 32.19 / 31.99 | **−41.4%** | same |
| `synth-7200s.mp3` | 16 000 | 1 | yes | 10 | 36.97 / 36.16 | 9.43 / 9.22 | **−74.5%** | differs |

**On every NON-final chunk — the case the `phaze-w55w1` gate exists for — `endTime` beats the
`Trimmer` gate: −45.2%, −41.4%, −7.2%.** That is the headline of this table. `phaze-b2qs9` §4c
measured the `Trimmer` gate at 18.5–36% and found it did not scale with the boundary; a real
`endTime` inside the loader stops the demuxer itself, and on the 48 kHz file it removes **45%** of
a chunk that the gate could not. **The gate becomes unnecessary, not merely improved.**

**The md5 column is an independent confirmation of §4c**, and it lines up exactly: the PCM differs
in precisely the two rows where a real seek happens *and* the ratio is not 1.0. Where `startTime`
is 0 (chunk 0, no seek) or the ratio is 1.0 (`synth-3600s.mp3` at 44 100), the two arms are
**byte-identical**. Nothing else differs.

**One row is a reproducible REGRESSION and is not explained.** `synth-3600s.mp3` chunk 1 costs
**+23.1%** with seek. It is the least favourable configuration on purpose — 60 windows of
fan-out, ratio 1.0 so decode is a `fastcopy`, and a *final* chunk, so the baseline is ungated and
is the cheapest arm the baseline ever has (`phaze-b2qs9` §4d saw the same "ungated final chunk is
cheapest" shape). Isolated decode for this exact case is **1.089 s seeked against 2.333 s
unseeked** in the same streaming mode, so the loader is doing less work and the extra ~9 s is
downstream of it, in the 60-branch `Scale`→`Trimmer` fan-out. The seek arm's cost is suspiciously
*constant* (49.4–50.4 s across both chunks) while the baseline's varies 40–54 s, which points at
scheduler/token-batching behaviour rather than at the patch. **This must be understood before
phaze adopts the patch** — it is the one result here that could turn a win into a loss on the fine
tier, and it is recorded as an open question rather than explained away.

Two integration findings came out of it, and they are worth more than the timings:

1. **A seeked loader emits a chunk-relative stream.** Its first sample is `startTime`, not 0, so
   every downstream `Trimmer` bound must be rebased by `chunk_start`. Get it wrong and the failure
   is **silent** — every window matches nothing and the chunk comes back empty. The harness asserts
   `n_decoded_full` for exactly this reason, and that assertion is what caught it. **Any phaze
   adoption must rebase the per-window `Trimmer` bounds.**
1. **Both arms produce byte-identical PCM.** The MD5 over the concatenated window buffers agrees
   between arms — see §6b for the surprise hidden inside that agreement.

## 6. Two incidental discoveries about phaze's *current* pipeline

Neither was being looked for. Both are properties of the code running in production today.

### 6a. `Resample` **does** have a ratio-1.0 short circuit — correcting `phaze-b2qs9` §4d

`phaze-b2qs9` §4d says "`MonoLoader` has no ratio-1.0 short circuit, but a 1.0 ratio is evidently
still far cheaper than 0.91875." The first clause is **wrong**: streaming
`src/algorithms/standard/resample.cpp` contains

```cpp
if (_data.src_ratio == 1.0) {
    fastcopy(_data.data_out, _data.data_in, _data.input_frames);
```

which bypasses libsamplerate entirely. **b2qs9's measurement stands and its conclusion is
strengthened** — the 5.2–7.7× penalty it measured on 48 kHz sources is now explained by mechanism
rather than inferred: ratio 1.0 is a `memcpy`, ratio 0.91875 is the full sinc resampler.
Independently reproduced here: 2.100 s vs 19.681 s for the same 3 600 s at the same tier rate,
a **9.4× penalty** for a non-unity ratio.

### 6b. `Trimmer` loses sample accuracy on long files — phaze's windows are not where it thinks

While proving the two benchmark arms equivalent, the concatenated PCM matched **but the window
lengths did not**: the baseline produced windows of 1 323 008 / 1 322 992 samples where the seeked
arm produced exactly 1 323 000. The stream is the same; the **cut points move**.

Cause: essentia's `Real` is `float32`, and `Trimmer` converts `startTime × sampleRate` in it. A
float32 mantissa is 24 bits, so past 2²⁴ = 16 777 216 samples — **380.4 s at 44.1 kHz** — the
representable spacing exceeds one sample and doubles every octave:

| position in file | exact sample | float32 result | error | grid spacing |
| ---: | ---: | ---: | ---: | ---: |
| 300 s | 13 230 000 | 13 230 000 | 0 | 1 |
| 380 s | 16 758 000 | 16 758 000 | 0 | 1 |
| 1 800 s | 79 380 000 | 79 380 000 | 0 | 8 |
| 3 090 s | 136 269 000 | 136 268 992 | **−8** | 16 |
| 20 279 s (5:38) | 894 303 900 | 894 303 872 | **−28** | 64 |
| 43 466 s (12:04) | 1 916 850 600 | 1 916 850 560 | **−40** | **128** |

**Consequence for phaze today:** every fine window past ~6 minutes into a file starts and ends off
the exact sample grid, by up to 8 samples at the 1-hour mark and up to ~128 samples (2.9 ms) at the
end of the longest corpus file. It is small, it is almost certainly below the threshold that moves
a descriptor, and **it has never been measured** — but it means the shipped window geometry is
approximate in a duration-dependent way, which is precisely the kind of thing that makes
"reproducible analysis" quietly untrue. The seek design removes it as a side effect, because the
loader tracks absolute position in `int64` samples and the `Trimmer` bounds become chunk-relative
(≤ 1 800 s) instead of absolute.

## 9. What this spike does NOT establish

Listed so nobody quotes it for something it did not measure.

1. **The TensorFlow-enabled source-build cost** (§2c). This is the number `phaze-a51jo` actually
   needs and it is still owed. 1 m 19 s is a floor from a no-TF, macOS-arm64 build.
1. **Any linux x86_64 result.** The production image is linux; everything here is macOS/arm64.
   ffmpeg versions match (§2d), which is the main risk retired, but the build has not been tried.
1. **End-to-end analyze wall clock.** §5a is decode only. The `phaze-b2qs9` methodology's
   end-to-end arm was not run, because it needs the TF models and a quiet node — and the burst
   node was correctly off-limits (`phaze-u1n7j` holds it).
1. **TF model output equivalence** (§4d). Classical descriptors are unmoved; the 34 graphs were
   not exercised.
1. **Real-corpus behaviour.** Synthetic audio only, by design. Real files differ in ways that
   matter to a seek — VBR without an index, broken/absent Xing headers, gapless metadata,
   concatenated streams. **Before adopting, a seek-accuracy pass over a real-corpus sample is
   mandatory**, and it must be run somewhere the results never leave.
1. **Peak RSS.** Not measured in either arm. Seek should reduce it (less audio decoded per chunk),
   but that is a hypothesis, and `phaze-u1n7j` owns the memory question.
1. **Why the fine-tier final chunk regresses by 23.1%** (§5c). Reproducible, isolated to the
   fan-out rather than the loader, and unexplained. It is the single result that could invert the
   verdict for the fine tier at ratio 1.0, and it is the first thing `phaze-a51jo` should chase.
