{# Status filter tabs -- ADAPTED (phaze-a6hm.2), not rewritten. The visual language is unchanged from the legacy proposals view: the same bottom-bordered nav, the same four tabs in the same order (the second now reads "Needs Review" per ADR-0008 -- phaze-tzy6s.17 -- over the unchanged `pending` value), the same blue underline on the active tab and the same pill-shaped count badge. What changed is that the markup no longer hardcodes WHERE it points. It used to build its own `/proposals/?status={{ value }}` URL and target `#proposal-content`, which is what tied it to a single page and left it orphaned when the v7 cutover replaced that page. Context contract (all required; no defaults, so a caller that forgets one fails loudly at render rather than silently emitting tabs that navigate somewhere wrong): * view -- a ListViewState (routers/view_state.py). Supplies BOTH the active-tab test (view.status) and the URL for every tab, via view.query(...). Because query() re-emits the whole state, clicking a tab preserves the search text, the page size and the sort -- the caller does not have to remember to thread them, and phaze-a6hm.10's sort params ride along with no edit to this file. * stats -- ProposalStats; the .total/.pending/.approved/.executed/.rejected/.failed counts in the badges. * tabs_url -- the path tabs navigate to (e.g. "/s/propose"). * tabs_target -- css selector of the swap target (e.g. "#propose-workspace-list"). `page=1` is reset on every tab: if the operator is on page 3 of Pending and clicks Approved, page 3 of the new filter is not where they meant to land, and may not exist at all. hx-push-url="true" puts the filtered URL in the address bar so the view is bookmarkable and survives Back. That is safe here ONLY because tabs_url is a real full-page route: a restore of the pushed URL re-renders the whole document (response_shape.py rule 2). Do NOT repoint this at a fragment-only endpoint. #}
{# phaze-tzy6s.17 / ADR-0008: the operator vocabulary is Needs Review / Approved / Blocked / Rejected. Only the LABEL changes here -- the tab VALUE stays the persisted `pending` status, because it is the query parameter the server filters on and the ADR is explicit that the UI mapping "does not migrate or collapse persisted statuses". Renaming the value would be a behavioural change to a bookmarkable URL; renaming the label is the conformance fix. phaze-te2g3 adds the "Executed" tab. Its absence was not a filter decision, it was an accounting hole: `All` is `stats.total`, which counts executed rows, so before this the badges beneath All did not add up to it and an executed proposal was reachable through no tab at all. The label is the persisted status verbatim rather than an ADR operator state because it is NOT one -- ADR-0008 folds `executed` into Approved, and this workspace deliberately does not (see ProposalStats): Approved here means "authorized, not yet dispatched", which is the distinction the Propose queue is for. phaze-5uh4u adds the "Blocked" tab, value `failed` (the persisted status, same value-vs-label split as every other tab here). ADR-0008's amendment is explicit that "a surface that shows this count set must show every term of it" -- this bar already shows total/pending/approved/executed/rejected, so a `failed` proposal was previously reachable through All only, with no tab, no badge and no way to filter down to it. Filtering to a blocked proposal to see why it failed is inspection, not approval action, so it stays inside what ADR-0008 restricts Propose to (generation and inspection) -- this tab does not add an authorization control, only a read-only filter, exactly like its four siblings. #} {% set tabs = [ ("all", "All", stats.total), ("pending", "Needs Review", stats.pending), ("approved", "Approved", stats.approved), ("executed", "Executed", stats.executed), ("failed", "Blocked", stats.failed), ("rejected", "Rejected", stats.rejected), ] %} {% for value, label, count in tabs %} {% set is_active = view.status == value %} {% endfor %}
