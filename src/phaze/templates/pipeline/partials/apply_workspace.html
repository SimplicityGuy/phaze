{# phaze-vvmh / phaze-tzy6s.12: the Apply (Execute) workspace -- the terminal step of the product's stated core workflow, "nothing moves without review, then execute", and the ONLY control in the product that moves bytes on disk. phaze-vvmh gave it an affordance at all (POST /execution/start previously had no reachable caller: an operator could approve five hundred proposals and had no control to dispatch them). phaze-tzy6s.12 turns that affordance into a real safety boundary. What changed, and why --------------------- The v7 workspace showed four aggregate counters and guarded dispatch with `hx-confirm`, a NATIVE browser prompt naming one number. That is the wrong instrument at this boundary twice over: 1. It cannot show a manifest. `window.confirm` renders one unstyled string, so "which operations, against which agents, what conflicts, what is excluded" had nowhere to go. The operator committed an irreversible batch knowing only its cardinality. 2. It is not the product's own safety pattern. The shared `ui.confirmation` dialog (the Phase 60 primitive set) is a real : focus-trapped, Escape-dismissable, themed, and screen-reader addressable via aria-labelledby. This workspace is its FIRST consumer. The manifest itself comes from `services/execution_preflight.get_execution_preflight`, which deliberately reuses `start_execution`'s OWN reads (detect_collisions / get_approved_proposals_grouped_by_agent / count_revoked_skipped_proposals) so it cannot drift from the dispatch it describes. See that module's D-10 record before adding a read. Exclusions are rendered, never omitted. Tag writes, duplicate resolution and cue sheets are NOT dispatched by this control (ADR-0008 puts tag authorization on its own append-only log), and an operation type silently absent from a manifest reads as "there is none of it". They appear with live counts and the stage that does own them. Disabled state carries visible text (R-4 / accessibility): the two reasons a dispatch cannot run -- an unresolved destination collision, or nothing approved yet -- read differently and need different next actions. Neither is a tooltip; `title=` alone is unreachable by keyboard and touch. Response sink: `#apply-execute-response` is a SIBLING of the trigger, never its ancestor (phaze-thd6) -- POST /execution/start answers with progress.html, collision_block.html or dispatch_in_progress.html, none of which re-renders the button.
