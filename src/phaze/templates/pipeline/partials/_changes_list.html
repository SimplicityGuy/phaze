{# phaze-tp52f: WHY sync() ENDS EACH REWRITE WITH htmx.process(). `setAttribute("hx-get", ...)` updates the DOM and NOTHING ELSE. htmx 2.0.10 reads a verb's path ONCE, in `processVerbs`, and closes over the string it read: const path = getAttributeValue(elt, 'hx-' + verb) // read at processNode time addTriggerHandler(elt, spec, nodeData, function (node, evt) { issueAjaxRequest(verb, path, elt, evt) // the captured string, forever }) Nothing re-reads the attribute at request time, so before this every rewrite below was inert on the wire: the DOM said `selected=` and the tab requested the URL it was SERVER-RENDERED with. Confirmed against the pinned 2.0.10 (shell.html loads htmx.org@2.0.10 with SRI), not against htmx in general -- if that pin ever moves, re-confirm rather than assume. WHAT THAT COST, measured in a browser (tests/browser/test_changes_facet_selection_wire.py): the operator could not DESELECT a row by unchecking it and switching facet tab. The uncheck rewrote the attributes, the tab shipped the stale server-rendered `selected=`, and the list came back with the row re-checked and "Approve selected eligible" re-enabled -- on EVERY switch, unboundedly, because each swap re-renders the tabs from the stale value it was just handed. Three consecutive rounds measured; it clears only by accident, when the destination tab happens not to contain the row (`x-init`'s visible-filter drops it). NO ROUTE SCOPES A WRITE FROM `selected=`. Both writes on this surface scope from the request BODY, which htmx serializes from the live DOM at request time: `PATCH /proposals/bulk` reads `review_tokens`/`proposal_ids` (routers/proposals.py) and the bulk tag write reads server-rendered hidden `review_tokens`. So the stale URL cannot widen a write directly. It widens one INDIRECTLY -- the resurrected checkbox IS the bulk scope -- and the resurrected state is visible on screen before the click, which is what keeps this a discarded-intent defect rather than a silent commit under a scope nobody chose. WHAT htmx.process() DOES TO phaze-tckiy'S GUARD: nothing. `htmx.process` -> `processNode`, which fires `htmx:beforeProcessNode`/`htmx:afterProcessNode` and NOT `htmx:load`. In 2.0.10 `htmx:load` has exactly two sources -- `makeAjaxLoadTask`, the deferred settle task, and the one-shot boot trigger on `document.body` -- so shell.html's `[data-hx-guard]` release listener is never invoked by this call. Even if it were, `releaseGuards` REMOVES `data-hx-guard` before it clears `disabled`, so a second pass matches nothing: release is idempotent by construction, not by this code avoiding it. Both halves are asserted, not argued (`test_the_guard_still_releases_exactly_once_across_repeated_syncs`). WHY IT IS SAFE TO RE-PROCESS THE FORM, whose subtree holds the two guarded buttons: `processNode` re-inits only elements whose `attributeHash` CHANGED (`maybeDeInitAndHash`), so untouched descendants are skipped. A released guard button has changed (both `data-hx-guard` and `disabled` are gone), so it IS re-inited -- and `initNode` does nothing to it: no verb, no `hx-boost` anywhere in these templates, no `hx-trigger`, and no `form` attribute, so not even `initButtonTracking`. `eltIsDisabled` is `closest(elt, '[hx-disable]')`, NOT the HTML `disabled` attribute, so a still-guarded button is not cleaned up either. The form's own button tracking survives because `initButtonTracking` re-adds the SAME named listeners (a no-op per the DOM spec) and `deInitNode` never removed them. `lastButtonClicked` lives in the form's internal data and IS wiped by the re-init, but sync() runs from a checkbox `@change` and from `x-init`, never between a submit click and its request -- and the bulk endpoint requires `action`, a BUTTON name/value htmx can only send via `lastButtonClicked`, so `test_the_bulk_patch_carries_the_live_selection_and_still_names_its_action` fails loudly (422) if that ever stops holding.
